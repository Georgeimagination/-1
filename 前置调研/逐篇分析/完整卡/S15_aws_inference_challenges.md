## 3. 来源定位、作者主张与机制

这份 AWS 指南把训练与推理的差别定位为生产系统问题：训练多为可计划、固定时长且以吞吐为主的任务，推理则面对连续或突发请求、每请求状态、低延迟和并发要求，系统因而需要弹性扩缩容、内存感知调度、缓存和流量治理。

[原文事实] AWS 在目标章节开头概括，训练负载“通常可预测、计算受限、面向吞吐”，推理负载“往往更不可预测、内存受限、延迟敏感”（PDF 第 12 页，印刷页 7；网页章节开头）。这句话是作者对常见工作负载的概括，不是本文实验验证出来的普遍定律。模型结构、批量、输入/输出长度和部署方式都可能改变瓶颈。

[原文事实] 目标表把差异分为六类。训练通常是计划好的固定时长运行，扩展需求可预先判断；推理可能持续或突发，依赖自动扩缩容、流量管理与路由。训练侧强调吞吐、加速器利用率、快速收敛、数据流水线、混合精度和自适应超参数；推理侧强调首词延迟（Time to First Token，TTFT）、并发、单请求延迟、单请求成本、模型压缩和缓存（PDF 第 12 至 13 页，印刷页 7 至 8）。

[原文事实] 资源状态也不同。目标表称训练期间大模型持续驻留，需要高效写 checkpoint，并处理长任务中的节点故障；推理需要因动态需求快速加载 checkpoint，模型规模和每请求状态又使服务常受内存约束（PDF 第 12 至 13 页）。相邻 right-sizing 章节把推理内存进一步拆成模型参数和键值缓存（key-value cache，KV cache）：权重内存随参数量和位宽变化，KV cache 随上下文 token 数、批量、注意力头数以及缓存精度大致增加（PDF 第 23 至 24 页，印刷页 18 至 19）。

[厂商设计意图] AWS 据此建议用每秒请求数（Requests per Second，RPS）、KV cache 使用率和请求队列长度驱动自动扩缩容，并指出扩容受到实例调配、容器镜像拉取、模型权重加载形成的冷启动延迟，以及区域容量可用性的限制（PDF 第 25 至 26 页，印刷页 20 至 21）。system-level optimizations 继续给出会话感知和延迟感知路由、批量调节、前缀缓存、分块预填充、连续批处理与最大序列长度调节（PDF 第 27 页，印刷页 22）。

可以从原文形成的因果链是：推理请求连续或突发，并携带随上下文与并发增长的每请求状态 → 系统目标从单次任务吞吐扩展为同时控制 TTFT、队列延迟、吞吐、并发和单请求成本 → 系统架构需要按 RPS、KV cache 与队列扩容，使用路由、批处理、缓存和张量并行管理容量。原文只支持到实例与服务系统这一层；由于没有芯片 HBM 带宽、峰值算力或片上数据流，不能再把这条链延伸成确定的芯片微架构结论。

关键断言的证据边界如下。

1. “训练通常计算受限、推理通常内存受限”来自目标章节的厂商定性总结。right-sizing 的权重与 KV cache 容量分析与该总结方向一致，但没有带宽测量、算术强度或训练侧对照，证据不足以把它写成无条件规律。
2. “推理需要低 TTFT 并服务很多并发会话”由目标表直接陈述，RPS、KV cache 与队列指标则给出系统操作化入口。指南没有提供 TTFT、并发数、请求长度、batch 或尾延迟实测，不能比较硬件。
3. “缓存、批处理和路由能改善推理效率”由 system-level optimizations 明确提出。它是工程建议，不是本文测得的效果；没有提升百分比、模型和硬件条件。
4. “同一资源可承担训练和推理”在 HyperPod 段落中被明确支持：同一计算资源可以同时用于两类负载，并通过 task governance 管理；self-managed inference 也可把原用于训练或评估的 EC2 容量重分配给推理（PDF 第 17、19 页）。这证明资源复用是可行部署选项，不证明同一芯片对两类负载都达到最优。

## 7. 跨图表推理与反例

[分析者推断] 把目标比较表与 right-sizing 章节连起来，可以得到“每请求状态使生产推理成为容量问题”的解释。目标表说推理因模型大小和每请求状态常受内存约束；right-sizing 再把状态落到权重与 KV cache，并指出 KV cache 随上下文和 batch 增长。替代解释是短上下文、小模型或大 batch 的推理也可能受计算限制，因此该结论只能作为常见服务场景的判断，置信度为中。

[分析者推断] 目标表与 auto-scaling、system-level optimizations 合看，推理效率并非芯片峰值指标的直接函数。请求突发、队列、冷启动、权重加载、会话 KV cache 局部性、batch 和序列长度都会改变用户可见延迟和资源利用率。由于本文没有硬件对照，最稳妥的结论是“系统软件与运行策略构成推理性能边界的一部分”，而不是“某类推理芯片必然更快”。

[分析者推断] 权重内存表能按位宽解释静态容量变化，却不能推出相同倍数的端到端速度或成本改善。量化还会影响 kernel、吞吐、精度、量化元数据和 KV cache 格式，指南没有测这些变量。置信度为高，因为缺失项在表中可直接确认。

HyperPod 与 self-managed inference 的 training compute reuse 是绝对二分的反例。同一批计算资源可以在训练和推理之间复用或重分配，说明部署层可以统一。这个反例只限制“训练硬件与推理硬件必须完全分开”的说法；它没有给训练和推理的性能、成本或能效对照，不能证明统一平台优于专用平台。

## 8. 适用时代、工作负载与缺失项

这份指南属于 2025 年末首次发布、2026 年 8 月生成 PDF 的云端生成式 AI 推理语境，面向已经训练好大型语言模型或多模态生成模型、准备上线生产服务的团队。目标章节讨论的是典型生产负载，不是针对某一模型或某一芯片的基准。相邻 right-sizing 示例覆盖 7B、13B、70B 参数规模，关注权重、KV cache、并发、上下文、RPS、TTFT 和实例扩缩容，适合解释现代自回归 LLM 服务的容量与调度约束。

较可迁移的部分是系统机制：在线请求的波动使容量必须动态调整；权重和 KV cache 共同决定静态与动态内存；batch 在延迟和吞吐之间取舍；缓存局部性、冷启动和队列会影响用户体验。不能直接迁移的是 50% KV cache 经验值、p5.48xlarge 容量例和所有 AWS 服务选择。模型的注意力结构、层数、上下文分布、精度、并发、服务等级、区域容量和软件版本都会改变结果。

来源未覆盖训练反向传播、梯度通信、优化器状态和激活保存，也没有训练完成时间或训练能耗。芯片侧几乎完全缺失：没有 AWS Inferentia、Trainium 或 H100 的峰值算力、HBM 带宽、片上 SRAM、数据流、互联带宽、功耗和有效利用率；唯一硬件数字是相邻容量示例中的 H100 80 GB。推理侧也缺少可复现实验、请求分布、模型版本、batch、上下文长度、采样参数、TTFT/逐词/尾延迟数值、功耗和成本测量。动态网页没有可确认的最后修改时间，PDF 生成时点也不能替代内容修订记录。
