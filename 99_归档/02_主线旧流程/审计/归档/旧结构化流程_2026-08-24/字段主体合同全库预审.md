# 字段主体合同全库预审

预审日期：2026 年 8 月 13 日  
状态：只读预审完成；尚未修改字段注册表、事实或字段要求  
明细：`审计/字段主体合同全库预审.csv`

## 为什么做这次预审

AWS Trainium3 的 Tensor Engine 时钟需要把 `FIELD-PHY-CLOCK` 挂到 component（组件），而正式字段注册表目前只允许 object（对象）。检查既有正式数据后发现，这不是单行问题：字段注册表的 `allowed_subject_kinds` 与正式事实或字段要求的实际目标之间还有多组不一致。当前正式校验器没有执行这项合同检查，所以 93,251 项校验通过不能证明字段主体合同闭合。

## 结果

预审逐行读取 `数据/facts.csv` 和 `数据/field-requirements.csv`，只统计恰有一个主体目标、且该目标类型不在字段注册值中的记录。共得到 132 行，涉及 26 个字段、28 组“字段、实际主体、登记主体”组合：

| 行类型 | 数量 |
|---|---:|
| 正式事实 | 8 |
| 字段要求 | 124 |
| 合计 | 132 |

其中 130 行的 `review_status` 已是 `reviewed`，2 行为 `needs_resolution`。这说明问题主要落在字段合同或历史主体建模，不能靠把行级状态退回草稿解决。

数量最多的组合是：

| 字段 | 实际主体 | 当前登记主体 | 行数 |
|---|---|---|---:|
| `FIELD-COMP-THROUGHPUT` | object | precision_path | 20 |
| `FIELD-MEM-CAPACITY` | object | component | 17 |
| `FIELD-INT-AGGREGATE-BW` | object | link | 17 |
| `FIELD-MEM-READ-BW` | object | component | 15 |
| `FIELD-CAP-IMPLEMENTATION-DETAIL` | object | capability | 11 |
| `FIELD-PHY-CLOCK` | component | object | 8 |
| `FIELD-DER-COMPUTE-BW-SPEC` | precision_path | object | 8 |
| `FIELD-PHY-CLOCK` | precision_path | object | 3 |

完整 132 行及其他 20 组组合保存在明细 CSV。CSV 的 SHA-256 为 `447ffbc05cbe387028037d5c30a8f218993712cfbe6063146a8c2b324d2855f5`。

## 与 AWS 包的关系

AWS 修正版提出把 `FIELD-PHY-CLOCK` 从 `object` 扩为 `object;component`。这个最小改动能覆盖四条 Trainium2 组件时钟事实、四条对应字段要求，以及 Trainium3 Tensor Engine 时钟候选，但仍有三条 H100 频率字段要求挂在 precision path（精度路径）。现有证据还不足以判断这三条应迁到组件、继续挂精度路径，或推动字段合同再加入 `precision_path`。

因此，AWS 包的最终复核可以单独裁决 `component` 扩展是否成立，但不得把它表述为全库字段主体问题已经关闭。全库修复要按 28 个组合逐组判断：有些应扩字段合同，有些应迁移字段要求主体，另一些可能需要拆成更具体的字段。不能按本 CSV 批量扩枚举或移动主键。

## 后续门槛

后续应建立独立的字段主体合同审计包，先逐组给出“扩合同、迁主体、拆字段、保留未决”四类裁决，再修改 `fields.csv`、受影响行和正式校验器。校验器至少要检查 facts 与 field-requirements 的唯一主体是否属于 `allowed_subject_kinds`；历史问题关闭前，这项规则先以审计模式报告，不能直接把 132 行全部阻断。
