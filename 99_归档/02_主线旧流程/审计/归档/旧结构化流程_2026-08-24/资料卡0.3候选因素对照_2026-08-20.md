# 资料卡 0.3 候选因素对照

日期：2026 年 8 月 20 日  
任务：`R1-TEMPLATE-CANDIDATE-ALIGN`  
结论：资料卡需要修改。芯片属性与芯片绑定机制进入属性字段，厂商定位和条件化实测分别保存；负载变量只作为实测条件，不能改写成芯片属性。

## 1. 判断口径

本轮把三个项目都视为前置调研：当前项目的 [训练芯片与推理芯片架构差异总结报告](../../01_前置调研-训练推理架构关注点/训练芯片与推理芯片架构差异总结报告.md)，历史项目 `调研v4` 的 [执行摘要](../../../调研-训练推理芯片调研/调研v4/00_总览/00_执行摘要.md) 与主题分析，以及 `调研-训练推理芯片调研-codex-v3` 的 [研究计划](../../../调研-训练推理芯片调研-codex-v3/RESEARCH_PLAN.md)、工作负载账本和阶段复核。它们用于发现正式调研可能需要观察什么，不负责证明某个因素已经是训练芯片与推理芯片的普遍差异。

候选因素是否进入资料卡，不以“已经全票确认”或“已经观察到统计差异”为前提，但必须先判断它属于哪一层：

| 层次 | 例子 | 在当前项目中的位置 |
|---|---|---|
| 芯片属性或芯片绑定机制 | 计算阵列、数据流、存储容量与带宽、互联拓扑、集合通信卸载、DMA、虚拟内存、硬件调度、RAS | 进入 `fields.csv` 和资料卡主体；无公开资料时登记缺失状态 |
| 厂商定位和产品约束 | 厂商目标用途定位、设计目标、功率散热约束、地区供应、公开价格 | 作为产品语境进入资料卡，但不当作微架构事实或实际负载变量 |
| 负载变量 | 模型大小、batch、上下文长度、MoE All-to-All 通信量、KV Cache 容量或迁移量 | 只在引用实测结果时进入 `condition-sets.csv`；不设芯片字段和完整度领域 |
| 工作负载映射结果 | 模型算术强度、状态是否容纳、通信时间下界、单位工作成本 | 留给后续比较或工作负载分析，不登记为芯片属性 |

这一区分决定了前置调研如何落地。例如，MoE 产生 All-to-All 是负载特征；芯片是否提供高注入带宽、适合的拓扑、路由或集合通信卸载，才是架构因素。KV Cache 需要迁移多少是模型与部署结果；芯片是否提供足够容量和带宽、DMA、页迁移、远程访问或专用管理机制，才进入资料卡。

## 2. C01 至 C20 的归属

| 候选编号 | 前置调研提示的问题 | 资料卡 0.3 的处理 |
|---|---|---|
| C01 | 训练、推理及细分阶段 | 阶段只作为实测条件；芯片侧记录执行模型、硬件控制与调度 |
| C02 | KV Cache 与推理状态 | 不记录模型状态容量或迁移量；保留存储容量、带宽、虚拟内存、DMA、远程访问和芯片绑定的 KV 管理机制 |
| C03 | 优化目标 | 以厂商目标用途定位、设计目标和部署约束记录产品语境，不预先作差异结论 |
| C04 | 输入、乘积、累加、输出和转换格式 | 属于芯片属性；沿用已有数值路径字段，并在模板中完整展开 |
| C05 | 预填充与逐 token 解码 | 作为 benchmark 阶段和长度条件；不设“预填充芯片属性”或“解码芯片属性” |
| C06 | batch、并发和请求率 | 只作测量条件；只有芯片绑定的队列、抢占或调度机制才作为属性 |
| C07 | HBM 容量 | 属于芯片或封装属性；新增来源明确给出的对象可分配容量，与物理总容量和模型状态需求分开 |
| C08 | HBM 与其他层级带宽 | 属于芯片属性；沿用读写、方向、铭牌与可持续带宽字段 |
| C09 | 算力、容量和带宽平衡 | 保留芯片规格配比；具体模型的算术强度和 Roofline 判断留给工作负载映射 |
| C10 | 计算组织、阵列和数据流 | 属于架构因素；模板显式展开阵列、指令 Tile 和发射宽度，新增数据流与驻留、硬件控制与调度 |
| C11 | 片上存储与局部性 | 即使尚未确认普遍差异也继续保留；使用既有层级、局部性、汇聚、管理、端口和带宽字段 |
| C12 | 互联、拓扑和通信 | 芯片侧记录协议、链路、带宽、拓扑、路由、延迟和卸载；不建立具体模型的通信事件账本 |
| C13 | 调度、隔离和服务质量 | 即使尚未确认普遍“必须实现”也保留候选；新增芯片绑定的硬件调度、软件调度、抢占、隔离和 QoS 字段 |
| C14 | 功耗、能效与部署 | 功耗、散热、形态和部署约束属于产品属性；每 token 能耗只作为带完整负载条件的 benchmark |
| C15 | 软件栈与可用性 | 新增框架、芯片绑定的调度机制和软件成熟度；厂商声明、文档、运行验证和 benchmark 分层 |
| C16 | 统一或可组合架构 | 由对象关系、计算单元、共享资源、数据流和能力组合表达，不新增主观评分 |
| C17 | MoE 路由和通信 | MoE 阶段和 All-to-All 量是负载变量；只有路由、派发、网络内处理或集合通信卸载机制进入资料卡 |
| C18 | 派生比较指标 | 尚未确认统一指标不构成删除理由，但只保留芯片侧可复算比值；负载映射指标另行分析 |
| C19 | 代际迁移和时代背景 | 使用架构关系、发布日期、可用日期和有效期；不把历史趋势写成单款芯片属性 |
| C20 | 证据、缺失和冲突边界 | 沿用来源链和缺失状态，并新增“负载变量不得改写成芯片属性”的自检项 |

C11、C13 和 C18 在当前前置调研中没有获得全票确认。0.3 仍保留相应芯片侧观察项，因为核验结果限制的是结论强度，不是候选字段的存在；同时也不借“候选因素”之名把负载量或推导结果塞进芯片字段。

## 3. 两个历史项目如何使用

`调研v4` 补出了软件成熟度、可靠性、容错、训练稳定性、成本、部署、供应和地区约束等候选方向。0.3 据此增加结构化 RAS 字段、软件成熟度、公开价格、市场准入和部署约束。制程、代工、封装和地区变体继续承载可核验的产品事实；宏观地缘判断和系统 TCO 不进入芯片属性。

`codex-v3` 的训练状态账本、工作负载场景、通信事件和 Roofline 记录说明，实测结果必须带模型、阶段、batch、长度、并行、设备数、软件和统计口径。0.3 因此扩展 `condition-sets.csv`，但这些列只负责限定测量，不成为芯片字段。历史项目中的 `qwen-*` 专用表、状态容量、逐事件通信量和模型 Roofline 结果没有复制到当前资料卡。

## 4. 正式修改

事实字段从 120 个增至 141 个，新增 21 个资料卡事实字段。其中 13 个记录芯片属性或芯片绑定机制，包括计算与控制 2 个、可分配容量 1 个、软件 3 个、虚拟化与 QoS 1 个、RAS 6 个；5 个记录厂商定位、产品约束和公开价格；另有 3 个记录绑定完整条件的 benchmark。没有新增工作负载状态容量、KV 迁移量、单次通信收发量、事件频率、通信时间下界或单位工作成本字段。

`condition-sets.csv` 从 21 列扩展到 43 列，增加 22 个实测条件列，包括细分阶段、模型或任务、batch、长度、并发、请求率、并行、设备数、调度、质量、服务、指标、统计和消息大小。200 条既有条件集的新增列保持为空，原值和原指纹不变。列合同从 324 个增至 346 个。

受控枚举从 71 组增至 76 组，并扩展 `field_domain`、`completeness_domain` 和 `capability_type`。特殊能力只新增转置/置换和媒体处理两类明确可落到硬件或芯片绑定实现的机制，没有把连续批处理、前缀缓存、激活下卸或推测解码直接注册成芯片属性。

完整度从 9 个领域扩展到 13 个，新增 `scheduling`、`reliability`、`benchmark` 和 `economics`。已有完整度记录的 45 个对象各补 4 条 `needs_review`，共 180 条；这表示尚未按 0.3 新口径回查，不表示对象缺少相应能力。负载和工作负载派生结果不设完整度领域。

## 5. 后续使用边界

0.3 完成的是资料卡可观察性，不是差异结论，也不是工作负载建模。后续每款芯片按 13 个完整度领域登记芯片事实、产品语境、条件化实测或相应缺失状态；只有资料中存在 benchmark 时，才填写负载条件。比较阶段可以用负载条件控制样本可比性，也可以另行建立工作负载模型解释为什么某项芯片属性重要，但二者不能合并为同一类字段。

如果 49 款芯片完成采集后某个芯片侧候选因素没有观察到差异，可以在比较报告中写“当前样本未见差异”或“差异主要由其他条件解释”，不应回头删除原始字段。相反，如果某个负载变量影响很大，也只能说明它改变了评价条件或设计需求，不能把它本身称为芯片架构差异。
