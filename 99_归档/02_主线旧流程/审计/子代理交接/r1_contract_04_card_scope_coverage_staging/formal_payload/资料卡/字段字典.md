# 资料卡字段字典

版本：0.4  
日期：2026 年 8 月 21 日  
适用范围：主线冻结名单中的 49 个裸片或单芯片封装对象

## 1. 使用原则

字段字典约束资料卡、结构化数据和来源审计。资料卡负责解释，`facts.csv` 保存唯一的规范事实，`fact-assertions.csv` 保存每份来源自己的原值、单位、定位和短上下文。正文中的关键数字先通过 `fact_id` 回到规范事实，再由逐来源断言定位原文。

芯片侧字段的纳入门槛是“有合理可能影响训练或推理取舍”，不是“已经证明训练芯片与推理芯片存在稳定差异”。前置调研发现的芯片结构、机制、软件绑定或产品约束应先进入统一资料卡，再由 49 个对象的同口径数据判断差异是否成立。模型大小、batch、上下文长度、MoE All-to-All 通信量和 KV Cache 迁移量属于负载变量，只能作为实测条件或后续工作负载分析的输入，不能注册成芯片属性。公开资料不足时登记缺失状态，不以缺失为由删字段；前置调研中的专题判断也不能直接写成某款芯片事实。

每条事实只描述一个对象、一个字段和一组不可再拆的条件。SKU、精度、稀疏模式、功耗模式、对象层级、带宽方向或文档版本不同，必须拆成不同记录。

来源原值和规范化值同时保存。规范化只做无歧义的单位换算，不把相近格式、相邻 SKU 或不同方向的带宽强行合并。

## 2. 对象和关系

### 2.1 四层对象

| `layer` | 含义 | 可以记录的事实 |
|---|---|---|
| `architecture` | 一代共享的计算核心、指令、数据流和数值路径 | 执行模型、指令形状、核心组成、首次支持的格式 |
| `silicon_package` | 裸片、芯粒或封装内实现 | 裸片数量、封装内互联、HBM 接口、面积、晶体管 |
| `product_sku` | 具体模组、卡、云端加速器或可购买配置 | 启用单元、容量、频率、功耗、峰值和主机接口 |
| `system` | 底板、服务器、机架、Pod 或集群 | 设备数量、拓扑、聚合容量、系统带宽和最大规模 |

`object_type` 进一步细分为：

`architecture_generation`、`die`、`chiplet`、`package`、`module`、`card`、`cloud_accelerator`、`cloud_instance`、`baseboard`、`server`、`rack`、`pod`、`cluster`、`switch`。

资料卡阅读层的 `silicon_package` 同时容纳正式 `object_type=die` 和 `object_type=package`。它表示芯片实现层，不等于正式库中必须使用 `package`。

### 2.2 关系类型

| `relation_type` | 方向和含义 |
|---|---|
| `implements` | 具体对象实现某架构代际 |
| `contains` | 系统或封装包含下级对象 |
| `variant_of` | 容量、地区、功耗或形态变体 |
| `successor_of` | 明确的后继产品关系 |
| `marketed_as` | 芯片、卡、云配置或系统名称之间的市场映射 |
| `uses_interconnect` | 对象使用某互联或交换系统 |
| `offered_by_instance` | 云实例提供某加速器对象 |
| `historical_anchor_for` | 早期对象用于解释后续代际 |

`object-relations.csv` 保存关系。正式关系枚举使用 `implements_architecture`、`physically_contains`、`package_contains_die`、`sku_variant_of`、`card_uses_module`、`exposed_as_cloud_accelerator`、`instance_contains_accelerator`、`deployed_in_system`、`connected_by`、`supersedes_product` 和 `renamed_from`。上表的短名称只帮助阅读；写入 CSV 时必须使用正式枚举。系统聚合值不会通过关系自动继承给下级对象。

### 2.3 标识

标识使用大写 ASCII、数字和连字符，发布后不因显示名称变化而复用。

| 标识 | 推荐格式 |
|---|---|
| 架构 | `ARCH-<VENDOR>-<GENERATION>` |
| 具体对象 | `OBJ-<VENDOR>-<PRODUCT>-<VARIANT>` |
| 原子事实 | `FACT-<VENDOR>-<SUBJECT>-<FIELD>-<SERIAL>` |
| 来源 | `SRC-<YEAR>-<VENDOR>-<SHORT-NAME>-<VERSION>` |
| 来源家族 | `SFAM-<VENDOR>-<SHORT-NAME>` |
| 字段 | `FIELD-<DOMAIN>-<NAME>` |
| 派生指标 | `DER-<SUBJECT>-<METRIC>-<SERIAL>` |

### 3.1 卡级管理元数据

资料截止日是研究管理元数据，不是厂商可引用事实，因此不再使用 `FIELD-ID-DATA-CUTOFF`。`card-completeness.csv` 中每个对象唯一的 identity 行承载 `card_lifecycle`、`data_cutoff_date` 和 `scope_id`；其他领域的这三列必须为空。`assessed_date` 仍表示该领域的评估日，不能复制或改名为截止日。

`scope_id` 由 `清单/训练与推理芯片名单.md` 的正式名单分配，格式为 `SCOPE-001`、`SCOPE-002` 等稳定标识。`objects.csv.scope_id` 只在已有逐行审核证据时填写；共享设计组只保留技术复用含义，不参与 scope 主键判断。

`card_lifecycle` 使用 `legacy_unreconciled`、`draft`、`provisional`、`formal`、`superseded` 和 `archived`。`provisional` 与 `formal` 必须同时有 `data_cutoff_date`、`scope_id` 和已批准的覆盖 manifest；历史表头迁移初始使用 `legacy_unreconciled`，不追溯声称旧卡已闭合。

## 5. 计算资源字段

每条计算事实必须写明 `compute_unit_type`、`operation_type`、`input_format`、`accumulation_format`、`sparsity_mode`、`throughput_basis` 和 `scope`。

### 5.1 计算单元类型

正式 `component_type` 可写值为：`matrix`、`vector`、`scalar`、`control`、`special_function`、`memory_level`、`dma`、`async_copy`、`load_store`、`format_conversion`、`compression`、`decompression`、`video_encode`、`video_decode`、`image_decode`、`security`、`network_offload` 和 `other_fixed_function`。

来源中的“地址/控制”归入 `control`；“数据搬运”须按已公开机制拆成 `dma`、`async_copy` 或 `load_store`，不能判断时才用 `other_fixed_function` 并解释原因。稀疏嵌入属于用途或能力描述，不是单独的 `component_type`；集合通信只有存在硬件卸载证据时才写 `network_offload`，软件库支持写在软件或特殊能力记录中。

### 5.2 计算字段

| `field_id` | 中文名称 | 说明 |
|---|---|---|
| `FIELD-COMP-UNIT-NAME` | 单元名称 | 厂商名称和通用类别同时保存 |
| `FIELD-COMP-UNIT-COUNT` | 单元数量 | 物理、启用或逻辑数量要注明 |
| `FIELD-COMP-EXECUTION` | 执行模型 | SIMT、SIMD、脉动阵列、空间数据流、静态调度等 |
| `FIELD-COMP-ARRAY-SHAPE` | 物理阵列形状 | 与指令 Tile 分开 |
| `FIELD-COMP-INSTRUCTION-TILE` | 指令或算子 Tile | 指令支持范围和约束 |
| `FIELD-COMP-DATAFLOW-RESIDENCY` | 数据流与驻留策略 | 记录数据复用、驻留、流送和结果回写，与执行模型分开 |
| `FIELD-COMP-CONTROL-SCHEDULING` | 硬件控制与调度 | 记录发射、依赖、同步、抢占或静态编排机制 |
| `FIELD-COMP-THROUGHPUT` | 吞吐 | TFLOP/s、TOPS、op/cycle 等 |
| `FIELD-COMP-COUNT-RULE` | 运算计数规则 | 一次乘加计 1 次还是 2 次 |
| `FIELD-COMP-CONCURRENCY` | 并发关系 | 与其他单元能否同时达到峰值 |
| `FIELD-COMP-SHARED-RESOURCE` | 共享资源 | 发射、寄存器、存储端口、功耗等 |
| `FIELD-COMP-UTILIZATION-LIMIT` | 利用率限制 | 小矩阵、窄矩阵、小批量和不规则形状 |

“总算力”只保留厂商原始标签。矩阵、向量、标量和特殊函数吞吐不能在没有并发证据时相加。

### 8.2 带宽方向和基础

`bandwidth_direction`：

`tx`、`rx`、`per_direction_symmetric`、`bidirectional_aggregate`、`half_duplex_shared`、`direction_not_specified`。

带宽流量口径由 `traffic_basis` 记录：

`raw_line_rate`、`encoded_line_rate`、`protocol_payload`、`application_payload`、`sustained_measured`、`vendor_nameplate`、`relative_only`、`not_specified`。

理论峰值、厂商实测、第三方实测和公开推导属于 `performance_basis`，使用 `theoretical_peak`、`vendor_measured`、`third_party_measured`、`public_derived` 或 `vendor_label_unresolved`，不能和流量口径写在同一个枚举里。

## 9. 大模型特殊能力

`implementation_level` 使用以下枚举：

`dedicated_physical_module`、`dedicated_instruction`、`configurable_engine`、`general_compute_path`、`network_offload`、`compiler_optimization`、`library_implementation`。是否未公开、未找到或不适用由 `field-requirements.csv` 的缺失状态记录，不能伪装成实现层级。

需要记录的 `capability_type` 包括：

`top_k`、`sort`、`moe_route`、`moe_dispatch`、`all_to_all`、`reduction`、`softmax`、`sampling`、`sparse_skip`、`compression`、`decompression`、`quantize`、`dequantize`、`kv_cache_management`、`attention_data_move`、`collective_offload`、`transpose_permute`、`media_processing`、`other`。

每条特殊能力事实写明模块、指令、通用执行单元或与芯片绑定的软件库。软件实现不能写成专用硬件。MoE 负载会发生 All-to-All、某个模型会迁移 KV Cache，都不是芯片事实；只有来源明确给出路由、集合通信卸载、复制、虚拟内存、远程访问或专门管理机制时，才记录对应能力。

## 10. 工作负载条件集

0.3 版把实测所需的工作负载条件直接扩展进 `condition-sets.csv`，不另建一套与正式事实平行的工作负载表。原有 `workload_stage` 保留训练、预填充、解码、服务等粗粒度阶段；新增 `workload_phase` 继续区分训练前向、反向、优化器更新、混合专家（Mixture of Experts，MoE）路由和服务调度等细分阶段。这些列只限定 benchmark、公开测量或条件化能力，不是芯片属性，也不单独建立负载完整度领域。

| 条件列 | 含义与使用边界 |
|---|---|
| `workload_phase` | 细分执行阶段；使用 `training_forward`、`training_backward`、`optimizer_update`、`prefill`、`decode`、`moe_route_dispatch`、`moe_expert_compute`、`moe_combine`、`serving_control`、`other` 或 `not_specified` |
| `data_role` | 权重、主权重、梯度、优化器状态、激活、KV Cache、工作区、通信缓冲、检查点、预留区或元数据等角色 |
| `workload_model`、`workload_operator` | 模型或工作负载名称与版本，以及算子、子图、通信事件或测试任务 |
| `batch_size`、`microbatch_size`、`global_batch_size` | 通用或推理批量、训练微批量和训练全局批量，不能互相代替 |
| `sequence_length`、`context_length`、`input_length`、`output_length` | 训练或通用序列长度、推理上下文总长度、输入和输出 token 长度 |
| `concurrency`、`request_rate_value`、`request_rate_unit` | 并发请求、序列或作业数，以及请求到达率和单位 |
| `parallelism`、`accelerator_count` | 数据、张量、流水线、上下文、序列或专家并行配置，以及参与记录的设备数 |
| `scheduling_policy` | 批处理、排队、路由、放置或抢占策略 |
| `quality_constraint`、`service_level_constraint` | 准确率、收敛、输出质量、延迟、吞吐、可用性或其他约束 |
| `metric_name`、`statistic_basis` | 指标细分及其单点、均值、中位数、分位数、极值或范围口径 |
| `message_size_bytes` | 单次通信消息的规范化字节数 |

KV Cache 指推理中保存注意力 Key 和 Value 的键值缓存。相同对象在不同模型、阶段、批量、并行、服务约束或软件版本下的实测记录必须使用不同 `condition_set_id`。没有 benchmark 时，不为芯片虚构代表负载。已有 200 个条件集新增列均为空，不改变原有语义和指纹；后续只有在新条件非空时，才按完整条件重算新记录的指纹。

## 11. 软件、调度、虚拟化与可靠性字段

### 11.1 软件、调度与虚拟化

| `field_id` | 中文名称 | 说明 |
|---|---|---|
| `FIELD-SW-FRAMEWORK` | 框架适配 | 记录框架、版本、后端和硬件对象范围 |
| `FIELD-SW-CHIP-BOUND-SCHEDULING` | 芯片绑定的工作调度机制 | 只记录厂商明确绑定该对象或软件栈的硬件队列、资源分配、作业放置、请求调度和检查点协同；某次部署采用的策略仍是条件 |
| `FIELD-SW-SUPPORT-MATURITY` | 软件支持成熟度 | 使用 `vendor_claimed`、`documented_supported`、`runnable_verified`、`benchmarked` 或 `not_specified` |
| `FIELD-VIRT-PREEMPTION-QOS` | 抢占、隔离与 QoS | 记录抢占粒度、资源隔离、优先级和服务质量机制 |

QoS（Quality of Service）指服务质量。新字段补充而不替代既有编程模型、编译器、运行时、算子库、通信库、动态形状、量化工具、资源分区和多租户字段。厂商声明、文档支持、可运行验证和带完整条件的公开基准必须分层记录。通用 Serving 策略或某次部署的 batch 和路由方案不写成芯片调度属性。

### 11.2 可靠性

| `field_id` | 中文名称 | 说明 |
|---|---|---|
| `FIELD-RAS-PROTECTION-SCOPE` | 保护覆盖范围 | 计算、存储、互联、控制或软件状态边界 |
| `FIELD-RAS-ERROR-DETECTION` | 错误与故障检测 | 奇偶校验、CRC、看门狗、冗余检查或其他机制 |
| `FIELD-RAS-CORRECTION-REPLAY` | 纠错、重试与重放 | 记录机制、触发条件和作用域 |
| `FIELD-RAS-RECOVERY` | 恢复与降级 | 复位、隔离、迁移、替换或降级运行边界 |
| `FIELD-RAS-TELEMETRY-BIST` | 遥测与自检 | 健康遥测、在线诊断和内建自测试（BIST） |
| `FIELD-RAS-CHECKPOINT-RESTART` | 检查点与重启支持 | 记录硬件、固件或软件栈覆盖的状态和重启边界 |

RAS（Reliability, Availability and Serviceability）指可靠性、可用性和可维护性，CRC（Cyclic Redundancy Check）指循环冗余校验，BIST（Built-In Self-Test）指内建自测试。以上字段与既有 ECC、故障隔离、静默数据错误和 RAS 总述字段共同使用；不能用系统可用性承诺反推单芯片机制。

## 12. 实测、能效和经济性字段

| `field_id` | 中文名称 | 说明 |
|---|---|---|
| `FIELD-BENCH-UTILIZATION` | 利用率与扩展效率 | 通过 `metric_name` 区分模型 FLOP 利用率（MFU）、硬件 FLOP 利用率（HFU）、内存带宽利用率（MBU）或扩展效率 |
| `FIELD-BENCH-ENERGY-PER-TOKEN` | 每 token 能耗 | 绑定模型、阶段、批量、服务约束、功耗口径和测量范围 |
| `FIELD-BENCH-TOKENS-PER-JOULE` | 单位能量 token 数 | 绑定与能耗指标相同的完整条件，不能脱离条件取倒数比较 |
| `FIELD-ECON-PUBLISHED-PRICE` | 公开价格 | 绑定具体对象、币种、地区、渠道、数量和有效日期 |

既有延迟、吞吐和功耗字段继续使用。`metric_name` 可区分 time-to-train、step time、首 token 时间（Time to First Token，TTFT）、每个输出 token 时间（Time per Output Token，TPOT）、端到端延迟、goodput、利用率和能效；`statistic_basis` 记录均值或尾延迟等统计口径。总体拥有成本（Total Cost of Ownership，TCO）和单位工作成本依赖负载与系统假设，只能在后续分析中计算，不能下放成芯片事实。

## 13. 派生指标

| `metric_id` | 名称 | 公式和限制 |
|---|---|---|
| `METRIC-COMPUTE-BW-SPEC` | 规格计算带宽比 | 同对象、同精度的矩阵稠密峰值除以铭牌带宽 |
| `METRIC-COMPUTE-BW-SUSTAINED` | 实测计算带宽比 | 同对象、同精度的矩阵稠密峰值除以可持续带宽 |
| `METRIC-CAPACITY-COMPUTE` | 容量算力比 | 某层容量除以同作用域矩阵稠密峰值 |
| `METRIC-MATRIX-VECTOR` | 矩阵向量吞吐比 | 两条路径条件和计数规则必须相容 |
| `METRIC-MOVE-MATRIX` | 搬运矩阵吞吐比 | 需要明确数据宽度和搬运方向 |
| `METRIC-INTERCONNECT-COMPUTE` | 互联注入算力比 | 每设备单向注入带宽与同设备矩阵峰值配对 |

`derived-metrics.csv` 保存芯片侧派生事实、公式、结果单位及作用域、精度和方向三项检查；`derived-inputs.csv` 一行连接一个输入 `fact_id` 并说明它是分子、分母、比例、偏移或其他输入。条件或作用域不一致时不计算。模型算术强度、状态容量适配、MoE 通信量和通信时间下界属于工作负载映射，不登记为芯片字段。

## 14. 受控状态

正式受控值以 `数据/enums.csv` 为准；本文只解释资料卡最常用的状态。新增枚举先更新注册表和校验器，再修改本文与模板。

### 14.1 产品状态

`available`、`cloud_available`、`production_ramp`、`announced`、`discontinued`、`rumor_only`。

`历史锚点` 是冻结名单中的项目纳入角色，不是厂商产品状态，因此 `product_status` 不再包含 `historical_anchor`。

### 14.2 事实、证据和解决状态

一条规范事实分三个维度记录，不能把“缺资料”和“事实冲突”都塞进同一个状态：

| 维度 | 枚举 | 含义 |
|---|---|---|
| `fact_kind` | `direct_statement`、`measured`、`derived` | 原文直接陈述、测量结果或公开推导 |
| `evidence_state` | `single_source`、`corroborated`、`third_party_only`、`source_with_caveat` | 当前证据是单一来源、已有交叉确认、只有第三方，或来源带明确限制 |
| `resolution_state` | `accepted`、`provisional`、`superseded`、`conflict_member`、`rejected` | 规范事实已接收、暂用、被新版替代、属于冲突组或已拒绝 |

缺失由 `field-requirements.csv` 保存：`not_public` 表示一手资料明确未公开，`not_found` 表示完成计划检索仍没有可靠结果，`not_applicable` 表示对象没有该项，`pending_verification` 表示尚未核对，`inaccessible_evidence` 表示已知资料存在但目前无法合法取得正文，`conflicting_unresolved` 表示可靠来源尚未调和。未知不是零，也不能在 `facts.csv` 写一条空值事实代替缺失要求。

### 14.3 字段主体合同

`fields.csv` 为每个字段保存两套主体合同。`allowed_subject_kinds` 约束规范事实可以挂在哪类实体上；`allowed_requirement_target_kinds` 约束字段要求可以在哪类实体上登记。两列使用按正式顺序排列、以分号分隔的实体类型，例如 `object;component`，但它们不是多值外键。

事实主体由 `facts.csv` 七个互斥目标列决定：对象、组件（包括存储层级组件）、链路、对象关系、精度路径、特殊能力或拓扑。字段要求使用同一组七类目标列，并由 `allowed_requirement_target_kinds` 单独约束登记范围。`value_available` 和 `conflicting_unresolved` 一般必须在同一目标、同一字段找到事实；`FIELD-ID-ARCH` 只有在目标存在唯一 `implements_architecture` 关系时，才允许沿该关系投影。

### 14.4 复核状态

各表统一使用 `draft`、`reviewed`、`needs_resolution`、`approved`。来源断言另外用 `extraction_status` 记录 `pending`、`extracted`、`source_checked` 或 `independently_reviewed`，避免把“已经抽取原文”和“事实已经批准”混成一个状态。

### 14.5 来源角色和筛选状态

`source_role`：

来源断言的 `claim_role` 使用 `identity`、`core_spec`、`architecture_mechanism`、`independent_validation`、`conflict_evidence`、`status_version`、`missing_status` 或 `other`。`lead_only` 是来源筛选状态，不是已经支持某条事实的断言角色。

`screening_status`：

`pending`、`selected`、`lead_only`、`redundant_covered`、`superseded`、`out_of_scope`、`inaccessible`、`rejected_unreliable`。入选后承担的具体职责另写入 `source-selected-roles.csv`，使用 `identity`、`core_spec`、`architecture_mechanism`、`independent_validation`、`conflict_evidence` 或 `status_version_evidence`。

## 15. 单位和规范化

- GB、TB、GB/s 和 TB/s 默认十进制；GiB、TiB 使用二进制。
- FLOP/s 与 OP/s 保留浮点或整数语义，不能只按数值换单位。
- bit/s 与 byte/s 只有在方向和编码开销明确时换算。
- 时钟统一可换为 Hz，原值仍保留。
- 延迟统一可换为 s 或 cycle，但必须保存频率和测试路径。
- 一次乘加的计数规则进入事实条件，不能静默假设为 2 FLOP。
- 百分比、倍数和“最高”值保留来源原始基准，不脱离比较对象。

## 16. 完整度

`card-completeness.csv` 按领域记录：

`identity`、`physical`、`compute`、`numerics`、`memory`、`interconnect`、`special_engines`、`software`、`scheduling`、`reliability`、`benchmark`、`economics`、`evidence`。

每个领域使用 `complete`、`partial`、`missing_public_data`、`not_applicable`、`needs_review`。完整度只表示资料状态，不评价产品能力。0.3 迁移为已有完整度记录的 45 个对象补建了调度、可靠性、实测和经济性 4 个新领域，初始状态统一为 `needs_review`；这表示尚未按新口径回查，不表示对象缺少相应能力。负载条件不设完整度领域。

0.4 表头迁移为 585 条旧记录追加三列，45 条 identity 行的 `card_lifecycle` 统一为 `legacy_unreconciled`，其他领域三列全空。只有已通过显式归档映射闭合的 identity 行才填 `scope_id`，不从显示名称猜测。


## 17. 正式表与校验

0.4 版继续使用 32 张 CSV 表：`数据/` 18 张，保存对象、实体、字段要求、规范事实和芯片侧派生指标；`最小参考资料库/` 14 张，保存来源家族、内容版本、访问入口、逐来源断言、筛选、覆盖、冲突和检索记录。`schema-columns.csv` 是 350 个列定义的唯一表头注册表，`fields.csv` 登记 140 个厂商事实字段和两套主体合同，`enums.csv` 登记 77 组受控枚举。`condition-sets.csv` 保持 43 列和 200 条既有条件集；资料截止日已移到 identity 完整度元数据。

正式冻结芯片卡从 `draft` 晋级到 `provisional` 或 `formal` 时，必须显式传入已批准的受控覆盖 manifest。manifest 对 140 个 field 和本卡可达的真实 target 做穷举闭包，每个预期 field-target pair 都必须有明确的覆盖 target 和唯一 requirement，或有受控的排除裁定及理由。无 manifest 的 legacy 模式只复现旧库基础检查，不构成 promotion 通过证明。

每次修改结构化数据后运行：

```powershell
& 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe' -NoProfile -ExecutionPolicy Bypass -File '.\scripts\validation\Validate-ResearchData.ps1' -RootPath '.' -CoverageManifestMode gate -CoverageManifestPath '.\审计\工作包覆盖清单\<work_package_id>'
```

校验器检查 32 张表的存在和表头、必填值、主外键、枚举、禁止分号多值外键、七目标互斥、文本与数值二选一、两套字段主体合同、同目标事实闭环、已接收事实的来源断言、冗余来源覆盖、缺失状态证据，以及派生指标输入和条件检查。默认 `gate` 模式会把主体合同不匹配判为失败；`audit` 模式只用于迁移前盘点。它不替代原文逐项核对。
